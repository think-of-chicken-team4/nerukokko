# 仕様書からの変更・追加の記録

最終更新：2026-10-09　作成：田村（Claude Code と作成）

設計時点の仕様書（`docs/full-spec.md`・`docs/software-spec.md` ver4・`docs/ble-protocol.md`）から、**実装で変えたこと・書き足したこと・まだ決めていないこと**をまとめたものです。
メンバーへの共有と、発表資料・報告書を書くときの確認に使います。

- 決めた経緯の詳細は `docs/dev-plan.md` の §8「決定ログ」、未決事項は §9 にあります。この文書はその要約と、仕様書のどこが変わったかの対応表です。
- 今の正しい仕様は `CLAUDE.md` §4 の順（マイグレーション → `api-spec.md` → `ble-protocol.md` → `dev-plan.md` → 仕様書）です。この文書と食い違ったら、そちらが正です。
- **仕様書と違う実装をしたとき、仕様書にない決まりを足したときは、同じ PR でこの文書に1行追加する。**

| 区分 | 意味 |
|---|---|
| 変更 | 仕様書に書いてあることを変えた |
| 追加 | 仕様書に書いていなかったことを決めた |
| 未決 | 仕様書どおりでは問題があり、まだ決めていない |

## 2. 追加（仕様書に書いていなかったこと）

### 2-1. 睡眠の記録と起床

| ID | 内容 | 決めたこと | 理由 | 決定日 |
|---|---|---|---|---|
| A-01 | 睡眠スコアの計算方法 | 重み（40・15・15・15・15）は仕様書のまま。各項目の計算式を決め、データがない項目（例：レーダーがまだない＝呼吸）は除いて、残りの重みで計算し直す（dev-plan §6） | 仕様書には重みしかなかったため。実機がそろう前でもスコアを出せるようにするため | 10/2 |
| A-02 | 計測データをどの夜の記録に入れるか | 計測した時刻で振り分ける。記録の期間が重なるときは、後から始まった記録に入れる | 振り分け先を一つに決めるため | 10/2 |
| A-03 | たまごが巣に戻らないまま残った記録 | 起床予定から3時間たっても巣に戻らなければ、サーバーが起床予定＋3時間を終わりとして記録を完了にし、採点する。朝の画面に「起床を検知できなかった」と出す（T-209。10分ごとの定期実行と、鶏の同期のときに処理する） | 充電検知の失敗や置き忘れで記録が何日も残り、何日分もの記録を一晩として採点してしまうため（10/9 に 164.6時間でスコア94 を確認） | 10/9 |
| A-04 | 朝のコメント | Gemini を組み込むまでは定型文。Gemini が使えないときの予備としても残す | 外部 API なしで全体の流れを先に通すため | 10/2 |
| A-05 | 起床予定の決め方 | 「眠りにつく」を押した時点で、次に鳴るアラームを起床予定にする。アラームがなければ8時間後。記録中にアラームを変えても今夜の起床予定は変わらない | 寝ている間に起床時刻が変わらないようにするため | 10/2・10/9 |

| A-17 | 鶏の登録 | 鶏の MAC アドレスは Raspberry Pi の Wi-Fi（`wlan0`）のものを使う。トークンは登録・再発行の直後に一度だけ画面に出す。「トークンの再発行」と「別の鶏に交換」ができる（api-spec §2） | 仕様書に「どの MAC か」がなかったため。トークンを後から見られないようにして、漏れる機会を減らすため | 10/9 |
| A-18 | たまごの場所の表示 | 鶏が報告した「たまごが巣にあるか・つながっているか」と、記録中かどうかから「巣で充電中／ベッドの上／巣の外」を出す。鶏の報告が2分より古ければ「わからない」 | たまごは鶏を通してしか状態を送れないため | 10/9 |
| A-19 | 就寝準備の画面 | 夕方確認で「就寝準備へ進む」を押すと就寝準備になる（6時間たつか「戻る」で夕方確認に戻る）。鶏・たまごの準備ができていなくても「眠りにつく」を押せる（警告を出す）。プロトタイプはボタンを押せなくしていた | デバイスがない・つながらない夜でも記録を始められるようにするため | 10/16 |
| A-20 | 週間の記録 | スコアの棒グラフは「起きた日」ごとに1本（7日分）。平均はその7本の平均。中止した夜はグラフに入れない（一覧には出る） | 仕様書は「直近7日のスコア推移」までだったため。日付をまたいで寝る夜も1日として数えるため | 10/16 |
| A-21 | レーダーの誤検知対策 | 呼吸数は「人がいて呼吸しているとき」だけ採用する。反射の強さ（`env_max`）で人の有無、ピーク位置のばらつき（`peak_std_mm`）で呼吸の有無を、直近10秒の中央値で判定する。人の有無は在床・離床のイベント（`presence_events`）にも使う | 公式の呼吸アルゴリズムは、前に何もなくても約7割で呼吸数を出すため（実機検証 C2、#16） | 10/16 |
| A-22 | テキスト会話の回数の上限 | アプリでのにわとりとの文字の会話は、1人1時間に30回まで。超えたら「少し休憩しよう」と返す | Gemini の無料枠を使い切らないため | 10/16 |
| A-23 | 夕方の就寝提案の計算 | 起きる時刻＝次のアラーム。推奨就寝時刻＝起きる時刻 − 7時間半（90分の睡眠の周期×5回）− 寝つくまでの時間（その人の直近7晩の平均、10〜60分）。アラームがなければ提案しない。理由文は Gemini | 仕様書には「Calendar 取得→推奨就寝時刻を Gemini で生成」とだけあり、計算方法がなかったため。時刻の計算は AI に任せず決まった式にした（毎回同じ結果になるように） | 10/16 |
