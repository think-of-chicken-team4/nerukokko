# 実機検証・調整タスク一覧

最終更新：2026-09-24　作成：田村（Claude Code と作成）

コードは AI（Claude Code）で書けますが、**実機を動かして確かめること・値を調整することは人にしかできません**。
この文書は、ソフトウェア担当が分担して進める実機検証の一覧と手順です。

- **担当**：岡田（たまご中心）・浅井（鶏中心）。田村はそのあいだコードを進める。

- 結果（測った値・うまくいかなかったこと・写真・ログ）は、**項目ごとの Issue にコメント**で残す。AI がコードを直すときの材料になる。
- しきい値やピン番号などを変えたら、その値と理由も Issue に書く。
- 困ったら、測った値・写真・ログを添えて田村に相談する（Claude Code に渡して原因を調べられる）。

## 3. 準備

### 3-1. 共通

```bash
git clone https://github.com/think-of-chicken-team4/nerukokko.git
cd nerukokko
git switch -c <自分の名前> origin/main     # 例：asai。岡田さんは既存の ren ブランチを使う
```

作業を始める前は毎回 `git pull` と `git merge origin/main` で最新にする（`CONTRIBUTING.md` §2）。

### 3-2. たまご（ESP32）

- VS Code ＋ PlatformIO 拡張を入れる。`firmware/egg` フォルダを開く。
- テストプログラムはビルド環境（`-e`）を切り替えて書き込む。書き込みとシリアルモニタを一度に行うコマンド：

```bash
cd firmware/egg
pio run -e hwtest_accel -t upload -t monitor      # E1（ほかの環境名は §1 の表を参照）
pio run -e esp32dev -t upload                     # 本番のファームウェアに戻す
```

VS Code の場合は、下のステータスバーで環境（例：`env:hwtest_accel`）を選んでから、Upload と Monitor を押してもよい。

### 3-3. 鶏（Raspberry Pi 3B）

- OS は **Raspberry Pi OS（32bit）** を入れる。レーダーを動かす Acconeer のサーバーが 32bit 用のため（64bit でも動かせるが手順が増える）。
- `sudo raspi-config` で SSH・I2C・SPI を有効にする。
- Python の仮想環境は、OS に最初から入っている gpiozero などを使えるように `--system-site-packages` を付けて作る。

```bash
cd nerukokko/firmware/chicken
sudo apt install -y libportaudio2 i2c-tools
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
pip install -r requirements.txt -r hwtest/requirements.txt
```

## 4. 各項目の内容

各項目は「なぜやるか → やること → 合格の目安 → Issue に書くこと」の順で書いてある。

### E1. 加速度センサーの接続と寝返りのしきい値 ★（岡田・Issue #10、関連 #3）

**なぜ**：部品表では SEN0142 は「MPU-6050（I2C 接続）」だが、今のコードはアナログ接続として読んでいる。どちらかを確かめないと、寝返りを正しく数えられない。寝返りの回数は睡眠スコアの材料になる。

**やること**
1. 現物の基板・型番を見る。I2C なら VCC・GND・SDA（GPIO21）・SCL（GPIO22）につなぐ。
2. `pio run -e hwtest_i2c_scan -t upload -t monitor` で、0x68 か 0x69 が見つかるか確認する。
3. `pio run -e hwtest_accel -t upload -t monitor` を実行する。最初に「MPU-6050 を見つけました」か「アナログ3軸として読みます」と出る。
4. たまごを置いたまま1分待ち、「変化量の最大」がどのくらいかを見る（ノイズの大きさ）。
5. ベッドの上に置いて実際に寝返りを10回する。「寝返り #n 検知」の回数を数える。
6. 検知が多すぎる・少なすぎるときは、シリアルモニタに `t0.08` のように入力してしきい値を変え、やり直す。

**合格の目安**：寝返り10回中8回以上を検知し、じっとしている5分間の誤検知が1回以下。

**Issue に書くこと**：センサーの種類（I2C かアナログか）、静止時のノイズ、決めたしきい値、10回中何回検知したか。

---

### E2. マイクの音量レベル（岡田・Issue #11、関連 #6）

**なぜ**：いびき・寝言は「音量がどれだけ大きくなったか」で判定する。その判定の基準にする値を、実際のマイクで測っておく必要がある。

**やること**
1. `pio run -e hwtest_mic -t upload -t monitor` を実行する。
2. シリアルに `1` を入力（ラベル「静か」）し、静かな部屋で30秒以上測る。
3. `2`（話し声）でたまごの近くで普通に話す、`3`（いびき）でスマホからいびきの音を流す。それぞれ30秒以上測る。
4. `s` を入力し、ラベルごとの集計を表示する。

**合格の目安**：「静か」と「いびき」の中央値に、はっきり差がある（目安：3倍以上）。

**Issue に書くこと**：`s` の集計結果をそのまま貼る。いびきの音源と、スマホとの距離。

---

### E3. 充電検知（巣に戻した判定） ★（岡田・Issue #12、関連 #5）

**なぜ**：「たまごを巣に戻したらアラームが止まる」は、この製品の一番の特徴（二度寝防止）。充電モジュールの STAT ピンは満充電のときにも「充電していない」と同じ表示になるため、**満充電の状態で巣に戻すと止まらない**おそれがある。これを実機で確かめる。

**やること**
1. STAT ピンを GPIO27 につなぎ、3.3V へのプルアップ抵抗（4.7k〜47kΩ）を付ける。
2. `pio run -e hwtest_dock -t upload -t monitor` を実行する。
3. 巣に置く／取り出すを10回ずつ行い、毎回「【判定】」が1回だけ出るかを見る。「ピン変化」が2回以上ならチャタリングがある。
4. **満充電の状態で巣に置いたとき**と、**巣に置いたまま満充電になったとき**の表示を確認する。STAT ピンの電圧をテスターでも測る。
5. うまくいかなければ、巣からの 5V を分圧して読む回路を試す（`platformio.ini` の説明を参照）。回路の変更は HW 担当と相談する。

**合格の目安**：満充電のときも含めて、20回中20回正しく判定される（二度寝防止の要なので妥協しない）。

**Issue に書くこと**：各パターンで何回正しく判定されたか、満充電のときの STAT の電圧、チャタリングの有無。

### E4. BLE 通信の安定性 ★（岡田・Issue #13）

**なぜ**：たまごのデータはすべて BLE で鶏に送られる。寝ている間に途切れると、寝返りやいびきの記録が抜ける。起床時の「巣に戻った」も BLE で伝わる。

**やること**（C1 が終わって、ラズパイが使えるようになってから）
1. たまごに本番のファームウェアを書き込む（`pio run -e esp32dev -t upload`）。
2. 鶏をベッド横の実際の置き場所に、たまごをベッドの上に置く。
3. ラズパイで `python3 hwtest/ble_monitor.py --minutes 30` を実行する。
4. たまごを布団の下に入れた状態でも同じように測る。
5. 途中でたまごの電源を入れ直し、自動で再接続されるか見る。

**合格の目安**：30分間の取りこぼしが1%以下。再接続が1分以内。

**Issue に書くこと**：終了時の「まとめ」と、見つけたときの電波の強さ（RSSI）。布団の上・下それぞれ。

---

### E5. バッテリーの持ち（岡田・Issue #14）

**なぜ**：たまごは一晩じゅう電池で動く。途中で切れると、朝の「巣に戻す」も検知できない。

**やること**
1. `pio run -e hwtest_battery -t upload` を書き込む（本番と同じ動作＋稼働時間を1分ごとに記録する）。
2. 満充電にしてから USB を外し、電池だけで動かす。できればラズパイで `ble_monitor.py --minutes 720` を動かしておく（最後にデータが届いた時刻が分かる）。
3. 電池が切れたら USB につなぎ、シリアルモニタで「前回の稼働時間」を読む。
4. **充電・放電中は目を離さない。燃えやすいものの近くに置かない。**

**合格の目安**：9時間以上（一晩＋余裕）。足りなければ、省電力化を AI に依頼する（dev-plan F-09）。

**Issue に書くこと**：稼働時間、ble_monitor の「最後にデータが届いた時刻」。

### C1. ラズパイのセットアップとピン割り当て ★（浅井・Issue #15・最初にやる）

**なぜ**：鶏にはレーダー・マイク・スピーカーアンプ・LED・センサー・ボタンをつなぐが、ラズパイのピンの一部はほかの機能と重なる。特に：
- レーダー基板（スイッチサイエンス SSCI-067232）は、**ラズパイの1〜26番ピンに直接差し込む形**で、SPI を使う。
- I2S（マイク・アンプ）の BCLK は GPIO18＝**12番ピン**、I2C は **3・5番ピン**で、どれもレーダー基板の下に隠れる。
- LED（WS2812B）でよく使われる GPIO18 は I2S と重なる。

ここを最初に決めないと、ほかの検証も本番のコードも進められない。

**やること**
1. §3-3 の手順で OS と Python の環境を用意する。
2. `python3 hwtest/check_setup.py` を実行し、結果を確認する。
3. レーダー基板の資料で、使っているピン（SPI 以外のイネーブル・割り込みなど）を確認する。
4. 下の「ピン割り当て案」で配線できるかを確かめる。レーダー基板の下のピン（3・5・12番など）をどう取り出すか（長いピンのスタッキングヘッダーを使う、レーダー基板を9ピン端子からジャンパー線でつなぐ、など）を決める。
5. `config.txt`（`/boot/firmware/config.txt`）に次を追加して再起動する。

```ini
dtparam=i2c_arm=on
dtparam=spi=on
dtparam=audio=off
dtoverlay=googlevoicehat-soundcard
```

`googlevoicehat-soundcard` は、I2S のマイクとアンプを同じ配線で使う設定（まずこれを試す。音が出ない・録れない場合は Issue で相談）。

**ピン割り当て案**（物理ピン番号。確かめたら Issue で確定版を報告する）

| 用途 | 信号 | GPIO | 物理ピン | 備考 |
|---|---|---|---|---|
| マイク・アンプ共通 | I2S BCLK | 18 | 12 | レーダー基板の下 |
| マイク・アンプ共通 | I2S LRCLK | 19 | 35 | |
| マイク（SPH0645）→ ラズパイ | I2S DIN | 20 | 38 | マイクの SEL は GND（左チャンネル） |
| ラズパイ → アンプ（MAX98357A） | I2S DOUT | 21 | 40 | アンプの VIN は 5V |
| 照度・温湿度センサー | I2C SDA / SCL | 2 / 3 | 3 / 5 | レーダー基板の下 |
| LED（WS2812B）のデータ | PWM0 | 12 | 32 | 330Ω を直列に。3.3V で点かなければレベル変換を検討 |
| トサカボタン | 入力（内部プルアップ） | 16 | 36 | もう片側は GND（34番ピン） |
| レーダー（A111） | SPI0 ＋ 基板の資料で確認 | 8〜11 など | 19・21・23・24 など | 1〜26番ピンに差し込む |

**合格の目安**：`check_setup.py` で I2C・SPI・音声デバイス・Bluetooth がすべて ✅ になり、ピン割り当ての確定版が決まる。

**Issue に書くこと**：`check_setup.py` の結果、確定したピン割り当て表、レーダー基板の下のピンをどう取り出したか（写真）。

### C2. ミリ波レーダー（A111） ★（岡田・Issue #16）

**なぜ**：呼吸数は睡眠スコアの材料（呼吸の安定性）で、ベッドにいるかどうかの判定にも使う。センサーの向き・距離で結果が大きく変わるので、置き場所を実機で決める必要がある。

**やること**（C1 のあと）
1. Acconeer の A111 用 SDK（Raspberry Pi 用）を入手し、ラズパイで `./out/acc_exploration_server_a111` を起動する。
   - **SDK が入手できない場合は、すぐに Issue で報告する**（A111 は古い製品のため、配布が終わっている可能性がある）。
2. 別のターミナルで `python3 hwtest/radar_test.py` を実行し、呼吸数が表示されるか見る。
3. ベッドに横になり、`python3 hwtest/radar_test.py --count` で、自分で数えた呼吸数と比べる。
4. 鶏の置き場所（距離・高さ・向き）を変えて、一番安定する位置を探す。ベッドまでの距離が 0.3〜0.8 m から外れる場合は `--range 0.5 1.2` のように範囲を変える。
5. ベッドから離れたときに「呼吸を検出できていません」になるかも確認する。

**合格の目安**：自分で数えた呼吸数との差が ±3回/分 以内。

**Issue に書くこと**：`--count` の結果（置き場所ごと）、一番よかった置き場所と距離（写真）、SDK の入手方法。

### C3. 温湿度・照度センサー（浅井・Issue #17、関連 #4）

**なぜ**：室温・湿度・明るさは睡眠スコアの「環境適合度」の材料。温湿度センサー（M0235-1747）は中のチップがまだ分からず、読み取りのコードが書けていない。

**やること**
1. センサーを I2C（3・5番ピン）につなぐ。
2. `python3 hwtest/env_sensor_test.py --count 12` を実行する。
3. 温湿度センサーが「見つかりません」と出たら、I2C ではない種類（DHT22 など）の可能性がある。**型番と写真を Issue #4 に書く**（AI が読み取りのコードを書く）。
4. 市販の温湿度計と並べて、値の差をメモする。照度は明るい部屋と真っ暗な部屋で比べる。

**合格の目安**：温度の差が ±1℃、湿度の差が ±5% 以内。暗くすると照度が 0 近くまで下がる。

**Issue に書くこと**：見つかったセンサーの種類とアドレス、市販品との差、明るい・暗いときの照度。

### C4. マイク（SPH0645）（浅井・Issue #18）

**なぜ**：鶏のマイクは、トサカボタンを押したときの音声会話に使う。声が小さすぎたり雑音が多かったりすると、AI が聞き取れない。

**やること**
1. `python3 hwtest/audio_test.py devices` で、I2S のデバイス（googlevoicehat など）が出るか確認する。
2. `python3 hwtest/audio_test.py --device <番号> record --seconds 5` で録音し、`play rec.wav` で聞き直す。
3. ベッドから話しかける距離（1〜2 m）で `meter` を使い、話したときの音量（dBFS）を見る。

**合格の目安**：1〜2 m 離れて話した声が聞き取れ、話したときの音量が −40 dBFS より大きい。

**Issue に書くこと**：`record` の結果（RMS・ピーク）、距離ごとの音量、聞き取れたか。

### C5. スピーカー ★（浅井・Issue #19）

**なぜ**：アラーム音で本当に起きられるか、夜中にうるさすぎないかは、実際に鳴らさないと分からない。

**やること**
1. `python3 hwtest/audio_test.py --device <番号> tone --volume 0.3` で音が出るか確認する。
2. `rooster --volume 0.3`・`0.6`・`1.0` と変えて鳴らし、枕の位置で聞いたときの大きさを比べる。スマホの騒音計アプリで測れるとよい。
3. 返事の声（音声会話）用に、`play` で録音した声を再生し、聞き取りやすい音量も決める。

**合格の目安**：寝ている人が起きられる大きさで、音割れしない。

**Issue に書くこと**：アラームに決めた音量（`--volume` の値）、そのときの騒音計の値、音割れの有無。

### C6. LED（WS2812B）（浅井・Issue #20）

**なぜ**：光アラーム（だんだん明るくして起こす）と、にわとりの感情表現に使う。明るさや色の見え方を実機で決める。

**やること**
1. `sudo .venv/bin/python hwtest/led_test.py --mode colors` で色が正しく出るか確認する。
2. `--mode sunrise --seconds 30` で、暗い部屋で光アラームを試す。
3. `--brightness` を変え、光アラームとして目が覚める明るさと、まぶしすぎない明るさを決める。

**合格の目安**：指定した色どおりに光り、ちらつかない。

**Issue に書くこと**：使ったピン、光アラームに決めた明るさ、ちらつきの有無（あればレベル変換が必要か相談）。

### C7. トサカボタン（浅井・Issue #21）

**なぜ**：ボタンは音声会話の開始に使う。1回押したのに2回反応すると、会話が二重に始まってしまう。

**やること**
1. ボタンを GPIO16（36番ピン）と GND（34番ピン）につなぐ。
2. `python3 hwtest/button_test.py --seconds 60` を実行し、20回押す（短く・長く・連打を混ぜる）。

**合格の目安**：20回押して、検出も20回。チャタリングがあっても、その揺れが 50ms 以下。

**Issue に書くこと**：終了時の「まとめ」。
